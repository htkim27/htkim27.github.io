> **[`omni-iot` Github Project](https://github.com/htkim27/omni-iot)**
> 아이언맨의 '자비스'처럼 집 안의 기기들을 음성으로 자연스럽게 제어하는 AI를 상상해 본 적 있으신가요? Omni-IoT는 누구나 자유롭게 개인화할 수 있는 **일반 가정용 데스크톱 환경에서 완벽히 로컬로 동작하는 양방향(Duplex) 음성 에이전트**를 구축하여 이러한 상상을 현실화하려고 합니다.

![로컬 PC에서 스마트홈 기기를 제어하는 Omni-IoT 음성 에이전트](/assets/omni_iot_latency_cover.png)

음성 챗봇 에이전트에서는 사용자가 발화를 마친 순간부터 챗봇의 첫 음성이 들리기까지의 Voice-to-Voice Latency(V2V Latency)가 대화의 자연스러움을 좌우합니다. 이번 글에서는 16GB VRAM 환경에서 동작하는 Omni-IoT의 V2V Latency를 줄이기 위해 하드웨어 활용, 추론 설정, 스트리밍 아키텍처를 차례로 점검하고 개선한 과정을 다룹니다.

## 대화라고 하기엔 너무 긴 침묵

Omni-IoT 챗봇의 구조는 아래와 같이 순차적(Sequential) 파이프라인을 따르고 있습니다.

```text
사용자 발화 종료 → 무음 감지(VAD, 600ms) → Omni모델(STT + Tool Use) → TTS → 오디오 재생
```

처음 파이프라인을 완성하고 코드를 돌렸을 때 생각보다 너무 느려서 당황했습니다. 사용자가 말을 끝내고 AI의 첫 대답을 듣기까지 무려 8초에서 12초라는 긴 대기 시간이 발생했기 때문입니다. 그래서 어떤 부분들을 놓쳤는지, 그리고 어떤 부분들을 개선해야 할지 몇 가지 확인해 보았습니다.

## 하드웨어 활용도 최적화: 병렬 연산이 제대로 되고 있는 지 확인

가장 먼저 확인한 것은 하드웨어 리소스 활용 여부였습니다. 챗봇의 기반 모델은 용량이 크기 때문에 일반 데스크톱 환경에서도 CPU 오프로딩 등을 효율적으로 지원하는 `llama.cpp`기반 서버를 활용하여 배포를 하고 있습니다. 그런데 설정을 확인해 보니, 처음 파이프라인을 돌렸을 때는 GPU에 모델 레이어를 단 하나도 올리지 않은 실수를 범했었다는 것을 깨달았습니다. 이처럼 연산을 100% CPU에 의존했던 초기 상태에서는 순수 대화(No Tool) 시 8.01초, IoT 기기 제어 등 Tool을 사용할 때는 12.10초라는 절망적인 속도가 나올 수밖에 없었습니다.

물론 16GB VRAM 환경에서 에이전트 기반 모델 전체를 GPU에 올릴 수는 없었기에, OOM 없이 안정적으로 구동 가능한 최적의 레이어 수를 찾고자 점진적으로 GPU 오프로딩 범위를 넓혀가며 테스트했습니다. 결과적으로 전체 48개 레이어 중 절반인 24개 레이어까지 GPU 올렸을 때 안정적인 챗봇 배포가 가능하였고, 순수 대화(No Tool) 지연 시간은 8.01초에서 4.84초(약 39.6% 단축), 대화 중 도구 사용(Tool Use) 시에는 12.10초에서 7.16초(약 40.8% 단축)로 성능이 향상되는 것을 확인하였습니다.

만약 로컬 모델을 구동할 때 연산 속도가 생각보다 너무 느리게 나온다면, 가장 먼저 모델 추론이 최적의 하드웨어 상에서 잘 이루어지고 있는지 모니터링해 보시기를 권장합니다. 그리고 주어진 시스템 자원 내에서 VRAM을 어느 정도까지 안정적으로 활용할 수 있는지 직접 테스트하며 최적화하는 과정이 필요합니다.

## 모델 추론 최적화: Flash Attention 적용
동료가 LLM 추론 환경에서 속도가 느리다고 말할 때, 저는 가장 먼저 추론 최적화 알고리즘을 활용하였는 지를 묻고는 합니다. `llama.cpp` 환경에서는 그 중 하나인 Flash Attention을 제공하고 있습니다. 어텐션 연산 시 발생하는 고대역폭 메모리(HBM)와 SRAM 간의 I/O 병목을 줄여 연산 효율을 극대화하는 원리로, 플래그 하나로 손쉽게 활성화할 수 있어 지연 시간을 얼마나 더 단축할 수 있을지 기대하며 적용해 보았습니다.

하지만 기대와 달리 개선 효과는 크지 않았습니다. 순수 대화(No Tool) 지연 시간은 4.84초에서 4.60초(약 5.0% 단축)로 줄어드는 데 그쳤고, Tool Use 시에도 7.16초에서 6.89초(약 3.7% 단축)로 미미한 차이만 보였습니다. 단일 모델 연산의 GPU 어텐션 연산을 아무리 쥐어짜더라도 CPU 오프로딩으로 인해 발생한 통신·CPU 병목에 묻혀버려, 체감되는 V2V Latency 개선 효과가 크지 않았습니다.

추론 최적화 옵션은 때로 연산 속도와 답변 품질 간의 트레이드오프(Trade-off)를 유발하기도 합니다. 따라서 유명한 최적화 옵션을 무작정 켜기보다는, 기술의 동작 원리를 명확히 이해하고 현재 시스템의 '진짜 병목'을 해소하는 데 실질적인 도움이 되는지 면밀히 따져보고 적용해야 한다는 점을 배웠습니다.

## 아키텍처의 최적화: True Streaming 도입

![Voice AI Pipeline Architecture](/assets/Voice%20AI%20Pipeline%20Architecture.svg)

기존 순차 구조에서는 모델이 전체 답변 생성을 마칠 때까지 TTS 엔진이 대기하는 블로킹(Blocking) 병목이 발생했습니다. 이를 해결하기 위해 답변 생성과 음성 합성을 시간 축에서 중첩하는 True Streaming 파이프라인을 구축했습니다. LLM이 생성하는 개별 토큰을 실시간 수신하되 음성 억양(Prosody)이 무너지지 않도록 문장 부호 단위로 끊어주었고, 첫 번째 유의미한 구절이 완성되는 즉시 TTS 합성 및 클라이언트 오디오 재생을 병렬로 시작하도록 설계했습니다. 그 결과 순수 대화(No Tool) 시 지연 시간은 4.60초에서 2.68초로 약 41.7% 단축되었으며, Tool Use 시에도 6.89초에서 5.69초로 약 17.4% 단축되었습니다.

아키텍처 개편만으로 체감 대기 시간을 줄여내면서 깨달은 점이 있습니다. 바로 개별 모델 하나하나의 연산 최적화에 신경 쓰는 것도 중요하지만, 실제 AI 시스템을 구축할 때는 연결되는 모델들 그리고 그 주위를 이루고 있는'AI 하네스(Harness)'라고 불리는 요소들이 서로 **데이터를 병목 없이 효율적으로 주고받을 수 있도록 전체적인 아키텍처 디자인을 최적화**하는 고민이 반드시 수반되어야 한다는 것입니다.

## 결론

![실험 요약: 사용자 체감 응답 대기 시간 변화](/assets/omni_iot_latency_chart.png)

실무나 개인 프로젝트를 막론하고, 엔지니어링 현장에서는 늘 무한한 컴퓨팅 파워 대신 빠듯한 하드웨어 자원과 타협해야 하는 순간이 찾아옵니다. 고성능 클라우드 인스턴스를 무제한으로 쓸 수 없는 상황에서 고비용의 멀티모달 모델을 띄우는 일은 언제나 큰 도전입니다. 이번 프로젝트 역시 16GB라는 가정용 VRAM 환경에서 지연 시간을 최적화 하기 위해 '제한된 자원 속에서 시스템을 이루고 있는 요소들을 종합적으로 고려하여 최적의 타협점을 찾아가는 엔지니어링 과정'이었습니다.

1. **하드웨어 모니터링과 가용 자원 프로파일링**: 모델 추론 속도가 느리다면 가장 먼저 의도한 하드웨어(GPU) 자원이 제대로 활용되고 있는지 확인해야 합니다. 나아가 제한된 환경에서는 무리한 전체 오프로딩보다, 시스템이 안정적으로 감당할 수 있는 VRAM 한계선을 직접 테스트하며 최적의 오프로딩 타협점을 찾아내는 엔지니어링 과정이 선행되어야 합니다.
2. **동작 메커니즘 이해와 진짜 병목 찾기**: Flash Attention과 같은 유명 추론 최적화 기법도 시스템의 근본적인 병목(PCIe 통신 및 메모리 대역폭)을 해소해주지는 못합니다. 때로는 속도와 품질 간의 트레이드오프가 존재하므로, 기법의 동작 원리를 명확히 이해하고 현재 시스템의 병목을 실질적으로 해결하는지 면밀히 따져보아야 합니다.
3. **단일 모델 최적화보다 파이프라인(AI 하네스) 설계의 혁신**: 개별 모델의 연산 속도를 쥐어짜는 것만으로는 블로킹(Blocking) 구조의 한계를 넘을 수 없습니다. 실제 AI 시스템 구축 시에는 연결된 모델들과 주변 컴포넌트(AI 하네스)들이 데이터를 병목 없이 효율적으로 주고받도록 시간 축에서 파이프라인을 비동기로 겹치는 아키텍처 레벨의 설계가 체감 지연 시간을 줄이는 데 가장 결정적인 역할을 합니다.
