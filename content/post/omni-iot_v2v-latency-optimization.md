집 안의 불을 음성으로 켜고 끄는 에이전트를 만들었는데, 말을 건 뒤 첫 대답을 듣기까지 12초가 걸렸다. 도구를 쓰지 않는 단순한 대화도 8초가 넘었다. 기능은 동작했지만, 이 정도로 침묵이 길면 대화를 이어가기 어려웠다.

[Omni-IoT](https://github.com/htkim27/omni-iot)는 외부 인터넷 없이 가정용 PC에서 동작하는 음성 에이전트를 만드는 개인 프로젝트다. 이번에는 응답 지연을 줄이기 위해 모델 실행 설정과 음성 처리 구조를 손봤다. 일반 대화는 **8.01초에서 2.68초**, 도구를 사용하는 요청은 **12.10초에서 5.69초**로 줄었다.

그 과정에서 가장 크게 달라진 것은 최적화를 바라보는 기준이었다. 처음에는 모델의 추론 속도에 관심이 쏠려 있었다. 그런데 답변을 음성으로 전달하는 과정을 들여다보니, **첫마디를 들려주기 전에 답변 전체가 완성되기를 기다리고 있었다.** 이번 포스트에서는 그 기다림을 줄여간 과정을 공유해보려 한다.

![Omni-IoT 로컬 음성 에이전트](../assets/omni_iot_latency_cover.png)

## 첫마디가 나오기까지 무엇을 기다리고 있었나

이 글에서 말하는 응답 지연은 **사용자가 말을 끝낸 순간부터 에이전트의 첫 음성이 들릴 때까지의 시간**이다. 답변 전체를 생성하거나 끝까지 재생하는 데 걸리는 시간과는 구분한다. 사용자가 말을 건 뒤 얼마나 오래 아무 반응도 듣지 못하는지부터 줄이고 싶었다.

처음 구현한 구조는 순차 처리였다. 약 0.6초의 침묵으로 사용자 발화가 끝났는지 확인하고, 모델이 음성을 이해해 답변 텍스트를 생성했다. 그 답변을 모두 받은 뒤에야 음성 합성 엔진(TTS)에 넘기고, 만들어진 음성을 재생했다. 도구를 사용하는 요청은 도구 실행까지 마친 후 대답을 시작했다.

![발화 종료 감지, 답변 생성, 음성 합성, 재생으로 이어지는 초기 구조](../assets/omni_iot_pipeline.png)

구현 흐름은 이해하기 쉬웠다. 앞 단계가 끝나면 결과를 다음 단계로 전달하면 됐다. 하지만 각 단계가 기다리는 시간은 고스란히 사용자의 침묵으로 쌓였다. 특히 모델이 답변을 생성하는 동안 TTS는 시작조차 하지 못했다. 첫 문장을 말할 수 있어도 마지막 문장이 나올 때까지 기다리는 구조였다.

## 먼저 모델 실행 설정부터 바로잡았다

구조를 바꾸기 전에 기본 설정부터 확인했다. 모델 실행에는 `llama.cpp`를 사용하고 있었는데, GPU에 연산을 넘기지 않은 채 CPU만으로 추론하고 있었다. 첫 번째로 고칠 문제는 명확했다.

사용 중인 GPU의 VRAM은 16GB였다. 모델 전체를 올리기에는 빠듯해서, GPU에 배치하는 레이어 수를 늘려가며 메모리 부족 오류가 나지 않는 설정을 찾았다. 당시 환경에서는 전체 48개 레이어 중 24개를 GPU에 배치하는 구성이 안정적이었다.

이 설정만으로 일반 대화의 응답 지연은 8.01초에서 **4.84초**, 도구 사용은 12.10초에서 **7.16초**로 줄었다. 두 경우 모두 약 40%의 감소였다. 복잡한 최적화에 앞서, 이미 가진 하드웨어를 제대로 사용하도록 바꾸는 것만으로도 개선 폭이 컸다.

다만 24개라는 숫자 자체가 다른 환경에서도 정답인 것은 아니다. 여기서 가져갈 교훈은 레이어 수보다, 실제 실행 설정과 메모리 사용량을 먼저 확인해야 한다는 점이었다.

이어서 Flash Attention을 적용했다. 기대와 달리 추가 개선은 작았다. 일반 대화는 4.84초에서 **4.60초**, 도구 사용은 7.16초에서 **6.89초**로 줄었다. 약 4~5%의 변화였다.

이 결과만으로 PCIe 전송이나 CPU 연산 중 무엇이 지연을 지배했는지는 단정할 수 없다. 그 원인을 구분하려면 구간별 측정이 더 필요하다. 여기서 확인한 것은 **이 환경에서 해당 옵션 하나로 줄어든 전체 응답 지연이 크지 않았다**는 사실이다. 다음으로는 답변 생성과 음성 합성 사이의 대기 구조를 바꿔보기로 했다.

## 답변 전체가 완성되기 전에 말하기 시작했다

기존 구조에서 TTS의 입력 단위는 완성된 답변이었다. 이를 생성 중인 답변의 짧은 구절로 바꿨다. 모델이 내보내는 텍스트를 모으다가 쉼표나 마침표처럼 구절을 나눌 지점이 나오면, 그 부분부터 TTS에 전달하는 방식이다.

![답변 생성과 음성 합성, 재생을 겹치는 스트리밍 구조](../assets/Voice%20AI%20Pipeline%20Architecture.svg)

이를 위해 세 단계가 이어져야 했다.

1. **텍스트를 구절 단위로 전달한다.** 모델의 전체 출력이 끝나기 전에, 먼저 생성된 구절을 음성 합성에 넘긴다.
2. **다음 구절 생성과 현재 구절의 음성 합성을 겹친다.** TTS가 첫 구절을 처리하는 동안 모델은 다음 텍스트를 생성한다.
3. **음성이 준비되는 대로 재생한다.** 나머지 답변의 합성이 끝날 때까지 오디오를 모아두지 않는다.

아래는 텍스트를 구절로 나누는 원리를 보여주는 축약 예시다. 실제 프로젝트 코드를 그대로 옮긴 것은 아니며, 동시 실행과 오디오 재생 처리는 생략했다.

```python
def iter_phrases(text_chunks):
    buffer = ""
    for chunk in text_chunks:
        # 모델의 출력 조각은 문장 경계와 일치하지 않을 수 있다.
        for char in chunk:
            buffer += char
            if char in ",.!?。！？":
                phrase = buffer.strip()
                if phrase:
                    yield phrase  # 완성된 구절부터 TTS 작업 큐에 전달한다.
                buffer = ""

    # 마지막 구절에 문장부호가 없어도 빠뜨리지 않는다.
    if buffer.strip():
        yield buffer.strip()
```

구절을 나누는 것만으로 동시 처리가 완성되지는 않는다. 각 구절의 합성과 재생이 끝날 때까지 모델 출력을 읽는 쪽도 기다리면, 앞서 없애려던 대기가 다시 생긴다. 생성된 구절을 넘기는 작업과 음성을 합성·재생하는 작업이 겹쳐 진행되어야 한다.

달라진 것은 첫 음성이 나오기 위한 조건이었다. 이전에는 답변 전체를 받아야 TTS를 시작할 수 있었다. 바뀐 구조에서는 첫 구절을 확보하고 그 음성이 준비되면 재생을 시작한다. 사용자가 첫 구절을 듣는 동안 다음 구절의 생성과 합성을 진행할 수 있게 된 것이다.

그 결과 일반 대화는 4.60초에서 **2.68초**로 약 42%, 도구 사용은 6.89초에서 **5.69초**로 약 17% 줄었다. 모델의 전체 답변을 더 빨리 생성했다는 뜻은 아니다. **첫 음성을 들려주기 위해 기다려야 하는 작업의 범위를 줄인 결과였다.**

물론 구절을 짧게 나누는 데도 한계가 있다. 첫 음성을 빨리 들려주더라도 뒤의 합성이 늦으면 재생 중간에 공백이 생길 수 있다. 쉼표와 마침표를 기준으로 나누는 방식도 시작점일 뿐이다. 분할 위치와 구절 길이에 따라 억양과 흐름이 달라질 수 있으므로, 첫 응답 시간과 함께 실제로 이어 듣기 좋은지도 확인해야 한다.

## 2초대로 줄어든 대화와 여전히 5초가 걸리는 요청

변경을 순서대로 누적한 결과는 다음과 같다.

| 실행 구성                       | 일반 대화 | 도구 사용 |
| ------------------------------- | --------: | --------: |
| CPU만 사용, 순차 처리           |    8.01초 |   12.10초 |
| GPU에 24개 레이어 배치          |    4.84초 |    7.16초 |
| Flash Attention 추가            |    4.60초 |    6.89초 |
| 답변 생성·음성 합성·재생을 겹침 |    2.68초 |    5.69초 |

_사용자 발화 종료부터 첫 음성 재생까지의 시간이다. 이 글에는 반복 측정 횟수와 지연 분포를 제시하지 않았으므로, 수치는 해당 환경의 관측 결과로 읽어주시면 좋겠다._

일반 대화는 처음보다 약 **67%**, 도구 사용은 약 **53%** 줄었다. 하드웨어 설정을 바로잡은 효과도 컸고, 그 위에서 처리 단계를 겹쳐 추가로 대기를 줄일 수 있었다. 두 변경이 각각 어느 구간에 영향을 줬는지 구분해서 보는 것이 이번 결과를 이해하는 데 중요하다.

도구 사용 요청에는 여전히 5.69초가 걸린다. 현재 구조는 도구 실행을 마친 뒤에야 응답을 시작한다. 스트리밍을 붙여도 그 이전의 기다림은 남는다. 일반 대화에서 얻은 개선을 모든 요청에 그대로 기대할 수 없는 이유다. 다만 두 요청 유형의 시간 차이 전체를 도구 실행 시간이라고 볼 수는 없다. 어느 구간에 시간이 얼마나 드는지는 별도로 측정해야 한다.

다음에는 도구를 실행하는 동안 요청을 받았다는 짧은 반응을 먼저 들려주는 방식을 시도해보려 한다. 예를 들어 “불을 켤게요”라는 반응과 실제 실행 결과를 나누어 전달하는 것이다. 이때 먼저 내보내는 말이 실행 성공을 뜻해서는 안 된다. 실패했다면 그 결과도 이어서 알려줘야 한다.

이 방식으로 첫 반응을 1초대로 줄이는 것이 다음 목표다. 아직 달성한 결과는 아니다. 앞으로는 **첫 반응까지의 시간과 실제 작업 완료까지의 시간**을 함께 보려고 한다. 반응이 빨라졌다는 이유만으로 기기 제어 자체도 빨라졌다고 판단하지 않기 위해서다.

## 다음 최적화에서도 먼저 살펴볼 것

처음에는 로컬 PC에서 큰 모델을 돌리니 느린 것이 당연하다고 생각하기 쉬웠다. 실제로 GPU를 활용하자 지연이 크게 줄었다. 하지만 그 설정을 고친 뒤에도, 첫 구절을 말하기 위해 답변 전체를 기다리는 구조가 남아 있었다.

이번 작업을 통해 다음에 살펴볼 질문이 조금 구체적이 되었다. **사용자에게 첫 결과를 전달하기 전에, 반드시 끝나야 하는 작업은 어디까지인가?** 음성 에이전트에서는 그 경계를 답변 전체에서 첫 구절로 옮길 수 있었다. 도구를 쓰는 대화에서는 요청을 받았다는 반응과 실행 결과를 어떻게 나누어 전달할지가 다음 과제다.

아직 자연스럽게 대화하는 음성 비서라고 부르기에는 남은 일이 많다. 그래도 이제는 막연히 더 빠른 모델을 찾기 전에, 사용자가 기다리는 동안 각 단계가 무엇을 하고 있는지부터 살펴보려고 한다.
